## 0. 一句话目标

用**真实 LLM API**跑七品类 × 三任务并发探针，实时盯轨迹，从失败**反向定位智能体通用缺陷并热修**，修完继续测。  
**交付物是更强的通用 Agent**，不是某一关功能尽善尽美。

---

## 1. 产品口径（锁定，勿偏）

| 原则 | 说明 |
|------|------|
| 探针不是验收玩法 | 任务只是压力源；绿勾 ≠ 展厅手感签字 |
| 失败必反推 | 读 messages / 工具轨迹 / diff / gate / dry-run → 修 `game_agent` / `agent_contracts` / `agent_workspace` / 路由 |
| 禁止专修单场景 | 不为一个 case 堆 Intent if；不为某一品类「尽善尽美」停工期 |
| 禁止 express | 有 Key 必须 `provider=agent`、`agent_rounds≥1`；禁 catalog 快车道顶替实现 |
| 模板冻结 | 不改 `templates/{genre}/core/**`；只改会话 workspace 与 Agent 层 |
| 有效才 harvest | 门禁失败 / partial / 否定态不入库有效 Learned Skill |

## 2. 任务矩阵（七品类 × 三任务）

每品类固定三类用户原话（语义不变；具体文案可沿用或微调脚本内 `TASKS`）：

| 代号 | 含义 | 期望行为（7.19 口径） |
|------|------|----------------------|
| **T1** | 增加一个简单功能 | 整句 goals → Agent 实现；可 enable catalog skill，但**不得**跳过 LLM 循环 |
| **T2** | 增加两个简单功能 | 同 T1；两 goals 均须有磁盘证据 |
| **T3** | 创造性全新功能 | 现场写会话 `core/scenes/config`；禁裸 enable 冒充 |

品类：`platformer` · `shmup` · `survivor` · `pingpong` · `fighting` · `parkour` · `racing`  
合计：**21 案 / 轮**。

任务文案与验收以：`05-工具脚本/e2e_7_19_live_three_tasks.py` 为准（7.18 旧脚本仅历史对照）。

## 3. 工作流（测 → 盯 → 修 → 再测）

```text
┌─────────────────────────────────────────────────────────┐
│ 0. 基线：pytest 绿（勿与 Live 并行）· 确认 LLM_API_KEY   │
└───────────────────────────┬─────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────┐
│ 1. 并发 Live：七品类×三任务（可 --only 分批）             │
│    生产入口 apply_nl_patch / run_game_agent               │
└───────────────────────────┬─────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────┐
│ 2. 实时监测：轮次 · 工具调用 · 写盘路径 · gate · dry-run │
│    报告落盘（messages / diffs / gate / rolled_back）      │
└───────────────────────────┬─────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────┐
│ 3. 分类失败（见 §4）→ 提炼「通用短板」一条                 │
└───────────────────────────┬─────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────┐
│ 4. 热修 Agent/门禁/工具 + 最小单测 → 复跑失败案 → 回归    │
└───────────────────────────┬─────────────────────────────┘
                            ▼
│ 5. 更新：本规范进度表 · 热修手册 · CHANGELOG · 对接文档   │
└─────────────────────────────────────────────────────────┘
```

**循环节奏建议**

1. 先跑 **1～2 品类 × 3 任务** 冒烟，确认报告与并发无打架。  
2. 再全量或分批并发（建议并发 **2～4**，避免 API/Godot 墙钟互杀）。  
3. 每发现一类通用缺陷：先修再继续，避免缺陷污染后续案结论。  
4. 单轮结束：汇总「暴露短板 / 已修 / 未修 / 下一轮」——**不要求 21/21 玩法完美**。

## 4. 缺陷分类与热修落点

| 现象（探针） | 优先怀疑 | 热修落点（示例） |
|--------------|----------|------------------|
| 读盘空转不写盘 | 催写/调度/observation 截断 | `game_agent` 催写 tip · 读写分池 |
| replace 零命中 | CRLF/LF · 陈旧 hash | `agent_workspace.replace_workspace_text` |
| 门禁绿但玩法被掏空 | 关键链整写 / 结构保真过松 | `gameplay_critical_paths` · done 锚点 |
| 只 enable 无实现 | 条件门禁 / goals 覆盖 | `assert_conditional_mechanics_landed` |
| 错工具 / 串品类 | Catalog 隔离 · 工具引导 | `catalog_for_prompt` · Intent hint |
| dry-run 红后乱修 | 回滚 / 错误回灌 | 动作级 snapshot · observation 正向化 |
| 轮次/墙钟半成品当成功 | salvage 交付口径 | `gate_passed=false` → 空 `sandbox_files` |
| 幻觉 API / 改冻结源 | 白名单 / 路径守卫 | 写盘校验 · 模板 hash |

**判定「可复用修复」的标准**：同一修法对 ≥2 品类或 ≥2 任务形态仍受益，或有单测锁住回归。

## 5. 工程入口与并发约束

### 5.1 脚本

| 脚本 | 用途 |
|------|------|
| `05-工具脚本/e2e_7_19_live_three_tasks.py` | **主矩阵**：七品类×三任务并行；禁 express；全轮轨迹落 `reports/` |
| `05-工具脚本/e2e_7_18_live_three_tasks.py` | 历史对照（验收口径已废 express，勿作主跑） |
| `05-工具脚本/sandbox_llm_inject_probe.py --live --case …` | **单案深挖**：失败后再盯 messages / 注入文案 |
| `cd backend && python -m pytest -q` | **热修后回归**；**禁止与 Live 同开** |

### 5.2 校准清单（`e2e_7_19` 已满足；复跑前抽查）

- [x] 有 Key 时 `provider == "agent"` 且 `agent_rounds >= 1`  
- [x] 无「catalog express / `agent_rounds=0` 业务成功」路径  
- [x] 每案保存：user 原话、rounds、工具序列、写盘 diff、gate、dry-run、`rolled_back`  
- [x] 报告目录独立（`reports/live_three_tasks/<stamp>/`；已 gitignore `reports/`）  
- [x] `templates/{genre}/core` 前后 hash 不变（R1–R3 复核）  
- [x] T1/T2 若口语点名 skill：允许 enable，但必须经 Agent 循环，且有运行时/磁盘证据  

### 5.3 并发与环境

| 约束 | 原因 |
|------|------|
| Live **勿与全量 pytest 并行** | `cleanup_orphan_workspaces` 可能删会话副本 |
| 建议 `ThreadPoolExecutor` 并发 2～4 | API 限流 · Godot dry-run · 墙钟 360s |
| 每案独立 `session_id` / workspace | 避免串写 |
| 需要 Key | 无 Key 只能 stub，不算本阶段 |

### 5.4 实时监测清单（每案）

盯这些即可定位，不必人肉玩满 21 局：

1. 是否第 1 轮起调用工具（尤其 `read_file` / `search_in_file`）  
2. 写盘是否 `replace_text` 优先、是否误 `write_file` 掏空关键链  
3. `gate_passed` / `partial` / `rolled_back`  
4. dry-run ERROR 是否回灌并自愈  
5. summary 声称是否 ⊆ 磁盘
