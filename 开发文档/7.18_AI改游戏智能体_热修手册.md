- `templates/{genre}/core` 冻结 hash 不变

## HF-1 · 掉落快车道/门禁对「通用掉落」过度触发

- **现象**：shmup 新造任务「敌机被击落小概率掉落一颗爱心，捡到回血」被识别成 laser/bomb 掉落，走了硬编码激光/炸弹的掉落快车道，回复「已把激光和炸弹改成敌机掉落物」——牛头不对马嘴；且 `assert_drop_loot_done` 是 laser/bomb 专用，会误伤正确的爱心实现。
- **根因**：`is_drop_loot_request` 只要命中「掉落/捡到」等词就为真，而掉落快车道 `_run_shmup_drop_loot_express` 与专用门禁把「所有掉落」都当成 laser/bomb 掉落处理。
- **修复**（允许层）：
  - `intent_router.py`：新增 `is_laser_bomb_drop_request(text)` = 掉落语义 **且** 点名激光/炸弹。
  - `game_agent.py`：shmup 掉落快车道触发条件、`enable_catalog_skill` 拦截，改用 `is_laser_bomb_drop_request`。
  - `agent_contracts.py`：`assert_drop_loot_done` 增 `genre` / `laser_bomb` 形参；仅 laser/bomb 掉落才强制 `powerup_types` 含 laser/bomb + `apply_powerup` 解锁 + shmup spawner/主场景保护；通用掉落只保留「禁按钮话术冒充 + 须写捡/拾取试玩说明」，实现证据交给通用门禁。
  - `sandbox_intent.py`：离线 stub 的掉落分支也改为仅 laser/bomb 才写 laser/bomb `powerup_types`。
- **验证**：shmup 3/3 通过；爱心掉落任务走 LLM 自由创作，写 `config/game_config.json` + `core/player_ship.gd`，dry-run 通过。单测 `test_intent_router / test_catalog_express_all_genres / test_agent_contracts` 全绿。

## HF-2 · done 门禁不跑 Godot 冒烟 → 语义错误/坏 .tscn 蒙混过关

- **现象**：全量首跑 create 任务里 fighting/pingpong/survivor/parkour 均 `ok=True` 通过门禁，但 Godot 实际加载报错：
  - fighting：`Could not resolve class "res://core/fighter.gd"`、`interrupt_dash()/try_block()` 未定义
  - pingpong：`Invalid access to property 'scored' on null instance`
  - survivor：`chest.tscn:15 Invalid parameter`、`get_viewport_rect() not found in base self`
  - parkour：`boost_pickup.tscn` 引用不存在资源、`Invalid parameter`
- **根因**：`run_done_gates` 只做 GDScript 语法 + 契约 API 静态检查，**不跑 Godot headless**；`apply_nl_patch` 调 `run_game_agent(run_dry_run=False)`。语义错误（未定义方法、错基类调用）、坏 `.tscn`、null 访问全部漏检。
- **修复**（允许层，`game_agent.py` / `llm_patch.py`）：
  - 门禁阶段：当本轮写入含 `.gd/.tscn`（新机制/新场景）时**强制** `dry_run_godot`，把 parse/script error 追加进 `gate_errors` 回灌给 LLM，令其在后续轮次自愈；仅改 config/enabled_skills 的快改不拉起 Godot（省时）。
  - `apply_nl_patch` 的 agent `max_rounds` 8→10，门禁失败中止阈值 4→6，给自愈留足预算。
  - 系统提示新增「新机制避坑」：preload/ext_resource 只指向已存在文件、只调真实存在的方法、视口用 `get_viewport().get_visible_rect()`、访问节点先判空、拿不准 .tscn 就用脚本 `add_child` 动态生成、新节点须真正挂进运行场景。
- **验证**：见下方「复跑记录」。

## HF-3 · GDScript 误写 Python 字面量 None/True/False

- **现象**：parkour 新造任务 LLM 在 `player_runner.gd` 写了 `None`（Python），Godot `Parse Error: Identifier "None" not declared`；`validate_gdscript` 静态检查漏过，只能靠 dry-run 晚发现，浪费自愈轮次。
- **根因**：`validate_gdscript` 未检测 Python 字面量。
- **修复**：`agent_contracts.validate_gdscript` 增检测（去字符串/注释后按整词）`None/True/False` → 提示应写 `null/true/false`。写文件前即拦截（`write_file` 前置校验），秒级反馈。

## HF-4 · done 门禁启发式对「被动/位移类新机制」误伤

- **现象**：pingpong「连续接5球球拍变长」代码其实已 dry-run 干净，但 agent 10 轮耗尽仍没成功 done；卡在两条启发式：①`how_to_play 须含触屏`（正则只认 点按/按钮）②`summary 覆盖 goals`（中文 token 命中）。被动机制的试玩说明是「碰到/穿过/接住」，不含"按钮"，被反复打回，耗光自愈预算。
- **根因**：触屏门禁与 goals 覆盖启发式过严，对合法创作误报。
- **修复**：
  - `run_done_gates`：触屏可玩判定放宽，接受位移/拾取交互词（碰到/碰/撞/穿过/踩/接住/走到/移动/拖动/靠近/吃到/捡）——被动机制由触屏拖动角色达成即算可玩。
  - `game_agent`：goals 覆盖启发式改为仅在 `summary` 近乎为空（<20 字）时才拦；声称⊆磁盘交给 `assert_claims`+dry-run 严格把关，不再用脆弱 token 命中浪费轮次。
- **验证**：pingpong 3/3 通过（create 26.7s 一次过）。

## HF-5 · dry-run 错误反馈缺定位与根因行，LLM 无从下手

- **现象**：parkour create 反复失败，最终 `Invalid access to property 'pressed' on null instance`。真因是 LLM 改 `main.tscn` 丢了原有 `RetryButton` 节点 → `game_manager._wire_buttons` get_node 到 null。但 dry-run 只抓 `SCRIPT ERROR` 行，**没抓根因行 `Node not found: RetryButton` 与定位行 `at: res://core/game_manager.gd:42`**，LLM 只看到"null.pressed"，无法定位。
- **根因**：`dry_run_godot` 错误抓取过窄（仅脚本解析类），且丢弃 Godot 紧跟的 `at: (res://…:行号)` 定位行。
- **修复**：
  - `dry_run_godot`：扩大命中（Node not found / Invalid access / already connected / could not resolve|preload / non-existent resource / invalid parameter 等运行时错），并为每条错误追加紧跟的 `at: res://…:NN` 定位行；去重。
  - 系统提示强化：改已有 .tscn 必须保留原节点、只增不删，首选新脚本 `add_child` 挂节点勿动 main.tscn 结构；「at: res://xxx.gd:NN」即出错文件行号，先 read_file 再精准改。

## HF-6 · 讲解员按钮未启动过游戏时无响应（人工测试发现）

- **现象**：讲解员演示按钮（跳!/踩怪/捡金币）只有在「游戏启动并关闭过」之后才会触发代码滚动定位+高亮；从未启动游戏就点，无任何响应。
- **根因**：`kiosk/edu/code-highlight.js` 的 `handleAction` 首行 `if (!pollingActive) return;`。`pollingActive` 只在游戏启动（`startPolling`）时置 true。讲解员按钮走 `simulateAction→handleAction`，被这个「游戏轮询状态」门控误挡——而 `simulateAction` 本就是"无 Godot 桥时手动模拟"，不该依赖游戏在跑。
- **修复**：`handleAction(actionId, {manual})`；`simulateAction` 传 `manual:true` 绕过 `pollingActive` 门控（含 fetch 后的二次门控与字幕），游戏轮询驱动的高亮仍受 `pollingActive` 约束。`index.html` code-highlight.js `?v=7.4-c09-27`（需硬刷新）。

## HF-7 · platformer 金币/怪物类需求改错地方 + 整文件重写破坏碰撞（人工测试发现）

- **现象**：横版闯关连续对话「每5金币无敌加速」→「地图没金币」→「还是没金币+怪物改小」→ 最终「金币收集不了、碰怪物子弹卡住不扣血」。智能体屡次声称已加金币但游戏里没有/收不到，且把碰撞/受伤改坏。
- **根因**：
  1. LLM 不了解 platformer 金币是 `core/level_01.gd` 程序化生成（`coin_chance`/`_add_coin`），去改了错误的地方或新建游离场景 → 金币不进收集链，"看着加了其实没用"。
  2. LLM 缩小怪物时改了 CharacterBody2D 根/CollisionShape 的 scale，或整文件重写 core 脚本，丢失 `notify_hazard`/`collected`/踩踏判定 → 收集失效、子弹卡住不扣血。
- **修复**（允许层）：
  - `genre_context.py` platformer playbook 补精确架构图：金币生成链（level_01 `coin_chance`/`_add_coin`→collectible.collected→game_manager `_coins`）、受伤链（player `notify_hazard`）、怪物改小只动 Sprite scale 勿动碰撞体、以及"改已有 core/*.gd 用最小 targeted 编辑禁整文件重写"。
  - `game_agent._AGENT_SYSTEM` 增全局最小编辑铁律 + "加金币/道具先查源码生成处，勿新建游离场景"。
- **验证**：复现「多加金币」→ LLM 正确改 `level_01.gd` coin_chance(0.38→0.60, cap→0.95)+额外 `_add_coin`；「怪物改小」→ 只改敌人 .tscn Sprite `scale=0.7`、碰撞体不变；收集/受伤/踩踏逻辑与 collectible 全部完好，dry-run 干净。

## HF-8 · 失败几次后强制上锁（用户核心诉求：允许翻车，不许摆烂拒绝）

- **现象**：多轮未达标时返回「智能体这轮没改成…请换个说法或再发一次…线索：未在限定轮次内完成（无 done）」——等于失败后上锁，用户被劝退。
- **根因**：`run_game_agent` 在轮次耗尽 / 门禁失败≥6 时 `raise ValueError`，`apply_nl_patch` 兜成硬失败拒绝话术。
- **修复**（`game_agent.py`）：轮次耗尽/门禁多次未过 **不再抛异常上锁**，改为 `_salvage_agent_return` 尽力交付：
  - 本轮有改动且能加载 → `ok=True · partial=True`，诚实说"尽力改了这些、可能不完美、不满意再说我接着改"，附重开提示。
  - 改动会导致游戏打不开 → 用「回合前快照」`_rollback_snapshot` 回滚本轮改动，保持可玩，诚实告知并邀请继续（绝不 brick）。
  - 本轮无改动 → 温和邀请补充细节，不用"换个说法/没改成"的上锁话术。
  - 仅无 Key / LLM 通信等真错误仍抛异常。
- **验证**：注入永不 done 的假 LLM：能加载→尽力交付 ok=True 保留文件；坏主场景脚本（坏 preload）→dry-run 失败→回滚 `core/game_manager.gd`、游戏恢复、返回非上锁话术。单测 133 passed。

## HF-9 · 失败语义未闭环：坏 JSON 仍上锁 + 回滚保「已坏基线」（parkour 人工对话暴露）

> **状态**：文档已记录缺口与修复计划；代码实修见本节「计划修复」→ 提交后对照实现。  
> **触发对话**（跑酷会话摘要）：二段跳没用 → 大需求冲刺（30s/无敌/彩虹/加速/吃币缩短充能）声称成功 →「人物消失」→ JSON `Expecting ',' delimiter` 旧式上锁 →「没生效再改」→ dry_run `Node not found: "../Player"` → salvage 回滚并声称「保持能正常玩」，但人物仍消失。

### 现象（用户可见）

1. 第 3 轮仍出现「智能体这轮没改成…请换个说法…线索：Expecting ',' delimiter」。
2. 第 4 轮 salvage 说「撤回、保持游戏能正常玩」，故障（人物消失）却仍在。
3. 成功口吻（「已修复所有编译错误」）与后续不可玩状态矛盾。

### 根因（对照代码）

| # | 缺口 | 代码落点 |
|---|------|----------|
| A | HF-8 只盖住 `run_game_agent` 内轮次/门禁耗尽；**LLM 坏 JSON / `ValueError` 在入口仍硬失败** | `llm_patch.apply_nl_patch` `except (ValueError, JSONDecodeError, …)` → 上锁话术（约 946–988 行） |
| B | salvage 回滚基准是**本轮前快照**，不是「最后用户可玩/可见基线」。上一轮已 `ok` 但埋下人物消失时，本轮修失败回滚 = **锁死坏状态**还声称可玩 | `game_agent._salvage_agent_return` + `pre_turn_snapshot` |
| C | dry-run 能挡「打不开」，**挡不住「开得了但角色 invisible / 错误 get_node 晚触发」**；成功门禁过弱 | `dry_run_godot` / done 门禁 |
| D | 故障句「人物消失」路由已指向 diagnose，但坏 JSON 路径绕过 Agent；salvage 回滚又抹掉半修好的路径补丁 | `intent_router` 故障正则 vs `llm_patch` 硬失败 |
| E | LLM 改 `_edu` hooks 臆造相对路径 `../Player`（相对 `/root/Main` 无效） | 会话 `parkour_hooks.gd` 类文件 |

### 产品原则（用户已确认）

- **允许翻车、不完美交付**；**禁止失败后上锁劝退**。
- **禁止把「加载能过但角色没了」包装成「游戏能正常玩」**。
- 故障反馈局：**先修盘，禁止叠新机制**；JSON/通信失败也应温和继续，不用「换个说法」。

### 计划修复（HF-9 实修清单）

1. **`apply_nl_patch`**：`ValueError` / `JSONDecodeError` / 可恢复业务失败 → 走与 salvage 同语义的软交付（`ok=True · partial=True`，无「没改成/换个说法」）；仅无 Key、真不可恢复 OS/配置错误才硬失败。网络类可再试。
2. **回滚话术诚实化**：回滚后若仍是故障局（人物消失等），**不得**声称「能正常玩」；应写「已撤回本轮会打不开的改法；**原先的问题可能还在**，请再说一次我继续修」。
3. **故障局压施工**：`bugfix` / Intent B 时强化 system/feedback：禁止写新冲刺/技能；优先 `diagnose_workspace` + 绝对节点路径 + `visible=true`。
4. **（可选增强）可玩基线**：回合开始前若 dry-run 已通过，额外记 `last_loadable_snapshot`；仅当本轮把「能加载」改成「不能加载」才回滚到该基线；若基线本身已是「用户报人物消失」，回滚后仍标 `playability_suspect=True`。
5. **单测**：坏 JSON 不返回上锁句；回滚故障局文案不含「能正常玩」假安慰。

### 验收口径

- 人为抛 `json.JSONDecodeError` / `ValueError("…")`：`ok=True`，文案无「没改成」「换个说法」。
- 故障反馈 + 本轮 dry-run 失败回滚：文案承认「原先问题可能还在」。
- 既有 HF-8 用例（能加载 partial / 坏 preload 回滚）仍绿。

- 七品类 × 3 任务（加1/加2/新造）真·LLM 端到端全部通过，均在临时工作区自由创作，`templates/*/core` 冻结未改。
