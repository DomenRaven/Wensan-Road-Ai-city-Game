## 0. 一句话故事

今天不是在「把某一款飞机游戏改完美」，而是用真实 Live 失败，把 **AI 改游戏智能体** 的验收从「模型自称做完」推进到 **机器预言机裁定完成**：接线（HF-14）→ 表现（HF-15）→ 禁虚空 Done / 同错早停（HF-15.1）。

**可对外讲的金句**：

> 创作自由交给 LLM；是否完工交给环境。叙事不能替代磁盘上的符号与接线。

**可对外讲的过程金句**：

> 不是「问 AI 怎么改」就结束，而是 **测出现象 → 一起诊断定位 → 人确认方案 → 再改 → 用同一把尺复测**。

**必须同时承认的事实**：

> 这两天的人机协作**并不总是一次抓对核心**。出现过方向打补丁、归因偏移、工具跟错对象；当前智能体也**远未完工**。案例若只写胜利叙事，会误导下一班学生。

**测修总原则（有对话原话可核，后期写入 HF-13 / 方向锁定）**：

> **原话（约 7.19）**：不要「遇到一个缺陷就打补丁」——「**补丁是补不完的**」；「对某个具体场景做补丁没有意义，**要改就对智能体本身进行修改**」；要通过开放读盘定位问题。  
> **同日探针口径**：从测试结果 / 轨迹**反向定位**智能体缺陷并热修；**不**把乒乓/单场景修到尽善尽美。  
> **后日复述（7.21）**：从产出与工作记录反向定位工作流**结构性**缺陷，而不是只针对用户**此次需求**打补丁。

详见 **§0.5**（原则与工作流演进 · 含证据分级）· **§10** · **§11**。

## 0.5 方法论：反向定位结构缺陷 · 工作流怎么走到今天

> 本节回答两件事：**(1) 我们凭什么修智能体？(2) 入口工作流试过哪几条路、为何弃用？**  
> **写法约束**：能核对对话/文档的写成「已证实」；仅能旁证的标「过渡态旁证」；产品方本次回忆但尚未找到更早书面命名的，标「口述复盘」——**禁止把推断写成当时已有正式阶段名**。

### 0.5.1 总原则：产出 / 轨迹 → 改智能体本身（禁止场景补丁债）

| 证据级 | 内容 | 出处 |
|--------|------|------|
| **已证实 · 原话** | 「不是说遇到一个缺陷就打补丁？因为**补丁是补不完的**，对某个具体场景做补丁没有意义，**要改就对智能体本身进行修改**」；目标是「通过开放读盘就能定位问题」。 | 对话 7.19（续工窗，大力扣杀/开放读盘讨论前后） |
| **已证实 · 原话** | 乒乓只是测试场景；每次测试应从结果分析智能体不足并完善智能体，**不要局限于把乒乓修到尽善尽美**。 | 对话 7.19 |
| **已证实 · 原话** | 真 LLM 七品类×三任务并发；实时监测；**探针反向定位缺陷并热修复**；不要求功能尽善尽美，只通过场景测试完善智能体。 | 对话 7.19（HF-13 立项口述） |
| **已证实 · 原话** | 「通过探针报出的问题来**反推完善智能体工作流**」。 | 对话 7.19 |
| **已写成规范** | HF-13：失败必反推通用 Agent；禁专修单场景 / Intent if / catalog express。方向锁定 §3「防测一次改一次」。总纲 G2/G11。 | `HF-13 施工规范` · `工作方向锁定` · `总体设计需求` |
| **口述复盘（7.21）** | 「反向定位工作流中的**结构性**缺陷」「补丁是**永远**打不完的」——与上列原话同旨；「结构性 / 永远」为后日概括用词，**更早对话里查到的是「补不完 / 改智能体本身 / 反向定位缺陷」**。 | 本案例撰写当日用户说明 |

**课堂上可板书的对立**（与原话一致）：

```text
场景补丁：  用户这句话坏了 → 给这句话 / 这个品类加 if
改智能体： 这句话暴露的洞 → 改入口路由 / 工具 / 门禁 / 早停，使同类洞不再出现
```

§4 的「测→诊→方案→改→复测」是同一原则的操作化：诊阶段要贴的是**根因标签（智能体层）**，不是「怎么让这一局过关」。

### 0.5.2 入口工作流怎么演进（证据分级）

「听懂后怎么开工」确实换过路。下面按**可核对事实**排列；阶段代号 W1/W2/W3 是**教学归纳标签**，不是当时文档里的正式枚举名。

```text
W1 语义命中 → 直接预制 / catalog express     【已证实：曾为主路径，且被明确否掉】
    ↓
过渡：Agent 已上、快车/两阶段设想仍在     【旁证 + 用户曾提案两阶段；「并行」为口述概括】
    ↓
W3 第 1 轮起 LLM 全开 · 禁语义命中走预制快车 【已证实：7.19 总纲 G1/G2/Q10 锁定】
```

| 标签 | 证据级 | 当时实际发生过什么 | 可核对材料 | 为何不够 / 如何被否 |
|------|--------|-------------------|------------|---------------------|
| **W1 · 语义命中 → 预制** | **已证实** | 口语命中 catalog 词 → express / Intent A **硬 enable**，抢在整句理解前；历史 E2E 大量「加功能」走过 catalog 快车道；掉落也曾误走 laser/bomb 快车 | 用户原话：不喜欢「识别到大力扣杀就直接启动预制链路、略过完整需求」；希望靠拢秒哒/WorkBuddy，预制最多当 Skill（对话 7.19）。文档：[`秒哒需求`](./7.19_AI改游戏智能体_秒哒式自由创作_需求说明_v1.0.md) §1.1；[`热修手册`](./7.18_AI改游戏智能体_热修手册.md) HF-1；热修手册注「14 个加功能曾走 catalog」 | 条件被吞；预制常不可感；「没生效」再 enable |
| **过渡 · Agent 与快车/固定流并存** | **旁证 + 口述** | **可核对的并存事实**：有 Key 已走 `run_game_agent`，同时一段时间内仍保留 express / 掉落 pre-LLM 快车（HF-1 先**收窄**而非关死；对接窗仍写「开启激光仍可 express 秒开」）；条件句仍可能先命中 Catalog（HF12-10）。**用户曾亲口提案的另一形态**：「第一次按**固定工作流**改盘验收，用户反馈没生效/异常后**再开放 LLM 全部功能**」（两阶段）——总纲随后写明 **Q10 两阶段固定工作流 = 废弃**、G1「无失败后再开全工具」。 | 对话 7.19 总纲重写需求；[`总体设计需求`](./7.19_AI改游戏智能体_总体设计需求_v1.0.md) G1/Q10；HF-12 债项与 drop-loot 工具化；7.18 对接「掉落物与调试」 | **说明**：文档里**没有**找到名为「语义命中与智能体判断并行」的正式阶段标题；该说法来自 **7.21 用户复盘口述**。教学上可用「过渡态」概括上述并存与两阶段提案，**不要写成当时已签发的产品阶段名**。 |
| **W3 · Agent 为主 · 禁预制快车** | **已证实** | 有 Key：**第 1 轮起** LLM 多工具全开；关 catalog express；Catalog/桥/Learned/Reference = 材料；Intent 仅软建议；禁单场景 Intent if | 用户拍板原话：「有 Key 一律 LLM 主导，从第一轮起就是 LLM 多工具循环…」（对话 7.19）。总纲 G1/G2/G11；方向锁定禁恢复 express；HF-13 探针 `provider=agent`、`agent_rounds≥1` | 轮次变贵（产品接受）；假完工改由门禁/预言机/早停（HF-14/15/15.1）接住 |

**阶段之间的诚实说明**：

1. **W1→否掉**：有用户原话 + 秒哒切片，证据最硬。  
2. **「并行」不宜写死**：更稳的写法是「过渡期：Agent 主路径与 express/固定流设想曾并存或先后被讨论」；其中**两阶段工作流**是用户提案后由总纲 **废弃**，与「语义∥Agent」并不完全同一件事。  
3. **HF-1 收窄掉落快车 ≠ 已禁 express**：前者是过渡修补；**7.19 关全品类 express**才是 W3。  
4. **今日 HF-15.1** 仍服从「改智能体本身」：Live 虚空 done → 通用完工裁定，不是 shmup 命数专用 if。

## 3. 对话与协作模式（可复用教室流程）

今日是 **多窗口流水线**，适合作为「人机协作开发」示范：

```text
① 总控 / 文档窗     → 写需求·施工·开工词·映射·校验；改入口索引
② Agent 施工窗     → 只贴开工词；按切片 H1–H7 / O1–O7 改代码+单测
③ 验收窗           → 只跑约定 pytest 簇；对声称做磁盘真实性对齐
④ Live 烟测窗      → 真 LLM + 盯 live_trace / watch_agent_live（跟对 session）
⑤ 复盘窗           → 根因写进足迹；决定下一 HF；禁止当场堆场景补丁
```

**协作纪律（课堂上可板书）**：

1. **探针 ≠ 交付**：七品类 Live 用来暴露通用短板，不把单局玩法修到尽善尽美。  
2. **声称 ⊆ 磁盘**：验收先 `grep` / 读 workspace，再信 summary。  
3. **文档状态三态**：立项 / 已确认开修 / 已落地——入口文档必须同步，否则新窗会做错题。  
4. **合成单测锁回归**：Live 贵且慢；`test_hf14/15/15_1` 是日常门禁。

## 4. 测 → 诊 → 方案 → 改 → 复测（人机协作主循环）

> **与 §0.5 的关系**：五步是操作规程；§0.5 是选型尺子——诊/方案阶段若滑向「只救这一局」，就违背「反向定位结构缺陷」。

今日真正可教的，不只是「改了哪些文件」，而是**人怎么带着智能体把问题钉死、再改、再验**。下面按课堂可复述的五步写，并串进当日真实回合。

### 4.0 总览（板书用）

```text
【测】Live / pytest / 人工点屏
        ↓ 现象（gate 红、烧轮、UI 看不见、前端报「网络」…）
【诊】人提问题 + Agent 读 live_trace / 盘面 / 代码
        ↓ 根因标签（虚空 done？L2 旁路？跟错 sid？删了共用 DB？）
【方案】人对齐选型：修通用门禁 / 写规范切片 / 禁场景 Intent
        ↓ 文档包（需求·施工·开工词）或口头拍板
【改】施工窗按切片改 contracts / agent / 单测（可换窗）
        ↓
【复测】约定验收簇 pytest →（可选）同题 Live 烟测 → 入口文档回写「已落地」
        ↓ 未过则回到【诊】，禁止「再加一句 tip 交差」
```

**人与 Agent 的分工（今日实际）**：

| 角色 | 人（讲解员 / 总控） | Cursor Agent |
|------|---------------------|--------------|
| 测 | 点 kiosk、发自然语言任务、看试玩与徽章 | 跑 pytest；拆 `live_trace`；列 workspace 符号 |
| 诊 | 决定「这是通用短板还是单局瑕疵」；纠偏错误归因 | 对照 thought/summary/evidence/磁盘；给根因候选 |
| 方案 | **拍板**修法与红线（禁 Judge / Intent / express） | 起草需求·施工切片·开工词；列候选方案利弊 |
| 改 | 确认开修；必要时人工验收 UI | 按 H1–H7 / O1–O7 改代码与单测 |
| 复测 | Live 烟测手感；决定是否入库/推送 | 复跑验收簇；声称 vs 磁盘对齐 |

### 4.1 【测】怎么测：先暴露现象，不急着下结论

今日用过三类测试，课堂要强调**分层**：

| 层 | 做什么 | 今日例子 | 能证明什么 |
|----|--------|----------|------------|
| A. 合成单测 | `pytest` 固定用例 | hf14 / hf15 / hf15_1 簇 | 门禁规则没回退 |
| B. Live 探针 | 真 LLM + 真 workspace | `62da7eab`、`d74d04ca` | 真实烧轮/过门行为 |
| C. 人工点测 | 看 HUD、打 Boss、横屏按钮 | 命数/HP 是否可见；工具栏是否贴底 | 玩家体感 |

**测时人怎么跟 Agent 合作**：

1. 人先说清现象：「任务二回滚了」「右上角没有命数」「前端写网络问题」。  
2. 人给出**可定位句柄**：session id、大约轮次、用户原话、截图。  
3. Agent 被要求：**先读证据再解释**——`live_trace.jsonl`、`.session_ai_log.jsonl`、盘上 `.gd/.tscn`，禁止空谈。

**反例（今日踩过）**：盯盘脚本挂在旧 sid `ec9bfaeb` → 测错对象 → 假阴性。  
**纪律**：测之前先对齐「当前会话路径」。

### 4.2 【诊】怎么诊：人提问，Agent 定位，人裁定标签

诊断不是让 Agent「猜为什么」，而是一起做**差分**：

| 对照项 | 问法 | `62da7eab` T4/T5 结论 |
|--------|------|------------------------|
| thought vs summary | 模型自己是否承认缺符号？ | thought 认缺 `add_life`，summary 仍写已实现 |
| evidence vs 磁盘 | `symbol` 在 path 里吗？ | 缺函数仍交 evidence / 非法形状 |
| gate 文案 | 是 L1、L2 还是 how_to_play？ | L2 errors=0 → **不是**「L2 太严」 |
| 轮次曲线 | 同错是否在空转？ | ~23 / ~31 轮反复 done→rollback |
| 工具观测 | replace 是否零命中仍 done？ | 有；观测未强制暴露新增符号 |

**人在诊断中的关键动作**：

1. **否掉诱人错因**：例如「是不是再加 tip？」「是不是把门禁放宽？」——今日否掉，因根因是 Hallucinated Success。  
2. **升维到通用机制**：从「shmup 命数没做好」升到「虚空 done 烧轮」——才允许开 HF-15.1。  
3. **要求 Agent 用业界/馆藏对照**：分层预言机、同错早停、环境裁定完成——避免发明第二套幻想 API。

**可复制的诊断提示词骨架**（给人贴给 Agent）：

```text
会话 {sid} 第 {n} 轮失败。请只做诊断、先别改代码：
```

## 5. 技术主线拆解（给学员的「问题→机制」）

### 5.1 HF-14 · 证据验收（接线）

**问题**：模型说「加了无敌/进度条」，但函数未接线或反馈轮无真 diff。  
**机制**：`done` / `self_check` 必须交 `evidence[]`；`assert_evidence_wired` 核定义与调用链；反馈轮无真改动硬回灌。  
**课堂类比**：实验报告必须写「仪器读数」，不能只写「实验成功」。

### 5.2 HF-15 · 预言机分层（L1 + L2）

**问题**：接线绿了，玩家仍看不见（假绿进度条、空 TextureRect）。  
**机制**：  
- **L1**：接线证据（含多 caller / 间接调用；拒非法复合 symbol）  
- **L2**：表现谓词（如 ProgressBar 的 value/ratio 写入、图标 texture/占位）  
**课堂类比**：电路通了（L1）≠ 灯泡亮了（L2）。

### 5.3 HF-15.1 · 虚空 Done / 同错早停

**问题（会话 `62da7eab` T4/T5）**：  
thought 已承认缺 `add_life`，summary 仍写「已实现」并反复 `done`；把 `.tscn` 路径、`->` 散文当 `wired_by`；烧满 20～30 轮。  

**根因标签**：Hallucinated Success / Premature Done（叙事替代观测）。  

**机制（环境裁定，而非再加一句 tip）**：

| 切片 | 规则 |
|------|------|
| H1 | 拒 `.tscn/.tres` 当 GD symbol；拒 `wired_by` 含 `->` |
| H2 | 回合初不存在的新符号须落在本轮 `written_paths` |
| H3 | 同归一化门禁错连续 ≥3 → 强制 `partial` 早停 |
| H4 | `replace_text` 成功附 `symbols_added` |
| H5 | 同轮失败 `self_check` 后 `done` 不得假过关 |
| H6 | goals≥4 肯定式 tip（建议拆批，不硬拒创作） |
| H7 | 单测 + 文档回写 |

**对照烟测**：HF-15.1 后会话 `d74d04ca` 同主题（命数/HP/Boss+2）**14 轮过门**，盘上符号与 HUD 节点齐备。

### 10.2 展开讲三条（分享时建议口述）

#### （1）AG-1：tip 指错靶心（HF-14 之前）

- **表象**：无敌/周期机制「说好了但玩起来不对」。  
- **协作惯性**：讨论容易滑向「模型分不清时间触发还是击杀触发」→ 想用提示词纠正语义。  
- **纠偏后的核心**：半成品交付——磁盘上有相关写入，但**接线/周期更新未闭合**；旧门禁「有改动就偏绿」。  
- **教训**：当 Agent（含协作用的 Cursor）给出「语义/提示词」方案时，人要用 **evidence⊆磁盘与调用链** 追问；否则会做出漂亮但无效的 tip 补丁。

#### （2）任务二回滚：差点当成「门禁太严」或「再教模型别撒谎」

- **表象**：`62da7eab` T4/T5 长时间 rollback，体验极差。  
- **错误引力 A**：放宽 done / 少验一点，让学生少看见失败。  
- **错误引力 B**：system tip「不要未实现就 done」。  
- **证据否决**：同一局 L2 报错为 0；thought 已承认缺 `add_life` 仍连 done；非法 evidence（tscn 路径、`->`）在空转。  
- **抓回的核心**：不是「验得太狠」，而是 **完工裁定太软弱 + 同错不早停**。  
- **教训**：失败很痛时，人机都容易选「减压方案」；要用 trace 数字否决情绪方案。

#### （3）P0 绿了仍翻车：阶段性胜利 ≠ 机制闭环

- HF-15 P0（L1+L2）验收簇通过后，人与协作 Agent 都可能产生「主线关了」的错觉。  
- 紧接着的 Live 用**大包命数需求**一捅，暴露的是另一层：虚空 done。  
- **教训**：每个 HF 只锁一层预言机；**绿灯只证明这一层**，证明不了玩家故事结束。复测必须「同题 Live」，不能只拿合成簇交差。

### 10.3 协作过程里「方向漂移」的常见句式（以后听见要警觉）

| 危险句式 | 可能在逃避的核心问题 |
|----------|----------------------|
| 「先给这个场景加个特殊判断」 | 通用门禁/工具缺陷 |
| 「提示词再写严厉一点」 | 环境未裁定完成 |
| 「是不是轮次太少了」 | 同错空转 / 虚空 done |
| 「前端说网络不行」 | 未分层查 health / 鉴权 / 会话 |
| 「单测都过了应该没问题」 | 未做同题 Live / 未核磁盘 |
| 「把冷却条再调好看点」 | 控件类型已旁路谓词，或根因在接线 |

**人的纠偏职责（写进教案）**：听到上表左列时，强制回到右列提问；要求 Agent 给出 **根因标签 + 证据指针**，再谈改代码。

### 10.4 为何仍要把走偏写进教学案例

1. 学生会模仿「问 AI → 直接改」；若不展示走偏，他们会以为专家从不偏航。  
2. 智能体（游戏内 Agent 与协作用 Cursor）**都会提供局部最优补丁**；评价补丁要靠产品红线与探针口径。  
3. 承认走偏，才能解释为什么流程里要有「确认开修」「诊阶段不改代码」「入口状态三态」。  
4. 走偏往往是 **W3 原则口头在、W1/过渡态手脚在**（§0.5）；不写演进史，听众会以为「禁 express」是一开始就有的智慧。

### 10.5 原则句在走偏里怎么用（口述可用）

当协作 Agent 提出「给这局加判断 / 再严厉一点 tip / 放宽门禁」时，人应复述原则句再选型：

> 不要给具体场景打补丁——**补丁补不完**；要改就改智能体本身（读盘/路由/门禁/早停）。  
> 请回答：根因在哪一层？修完后，**换一句同结构用户话**是否仍成立？

答不上「换一句仍成立」→ 多半是场景补丁，退回诊阶段。

## 11. 当前智能体仍不完善（诚实清单）

> **立场**：HF-14 / 15 / 15.1 是必要台阶，**不是终点**。下列问题在 2026-07-20/21 仍然成立；分享时不要假装「已经很强」。

### 11.1 能力与机制债（产品 Agent）

| 域 | 仍在的问题 | 为何伤人 |
|----|------------|----------|
| 观察层 | HF-15 **P1 Observe**（场景 UI 真观察）未做 | ReAct 缺可靠 Observe，易靠叙事补洞 |
| L2 完备性 | ColorRect / 非 ProgressBar「假进度」可旁路 | 门禁绿 ≠ 玩家看见「条在动」 |
| 大包 goals | 仅软 tip 建议拆批，**不硬拆** | 命数+Boss+难度一锅仍易虚空或半成品 |
| 错误可解释性 | 前端大量 catch 成「网络问题」 | 学生/教师无法自助分层排障 |
| 控件与证据形状 | 非法 evidence 已硬拒一批，模型仍会试探边角 | 需持续加形状与侧效应断言 |
| 品类泛化 | 烟测仍偏 shmup；七品类轮换未恢复常态 | 未知是否把 shmup 习惯当成全局 |
| Learned Skill | 脏条目/降权策略仍要人工维持 | 失败局经验可能污染后续 |
| 试玩与部署 | 教学机房 S2 路 B、证书公网扫码等并行债 | 课堂现场能力 ≠ Agent 改码能力 |

### 11.2 协作与工程债（人 + Cursor）

| 域 | 仍在的问题 |
|----|------------|
| 文档状态 | 多窗并行时，入口「立项/开修/落地」仍可能短暂不一致 |
| 观测工具 | `watch_agent_live` 默认易粘旧 sid；缺少「强制跟最新会话」的强提示 UX |
| 数据清理 | analytics 与 auth 同库，运维误删成本高（应用层应拆库或清理白名单） |
| 推送与基线 | 状态提交可能因网络未上远端；「本机绿」与「仓库绿」会分叉 |
| 全量回归 | 日常只跑 28 条验收簇；全量 pytest 仍有历史红/波动，不能假装全绿 |

### 11.3 分享时建议的「收束句」

> 我们证明了：**用测→诊→方案→改→复测，可以把一类核心缺陷（虚空 done）钉住并机制化。**  
> 我们不能证明：**智能体已经可靠到可无人值守进课堂。**  
> 下一阶段仍应继续暴露短板（轮换探针、Observe、L2 旁路、错误文案），而不是专修演示局。

### 11.4 工程待办备忘（原「未收口债」）

- HF-15 P1 Observe（场景 UI 观察工具）  
- L2 对 ColorRect 伪进度条的旁路补强  
- 前端错误文案露出真实原因（减少「网络问题」误导）  
- analytics / auth **拆库**或清理白名单，防止再误删登录态  
- `watch_agent_live` 默认跟踪最新 sid  
- `e324eaf` 及教学案例增补若未推送，网络恢复后补推
