## 2. HF-12 总验收原则

### 2.1 必须同时成立

| ID | 原则 | 完成定义 |
|----|------|----------|
| S1 | 读盘完整 | LLM 明确知道读到的是全文件还是分片；不存在无标记的聚合硬切 |
| S2 | 最小编辑可执行 | 已有大文件默认使用 patch/replace，不要求模型回传整文件 |
| S3 | 写盘事务化 | 未过静态/动态门禁的代码不作为稳定 workspace 版本交付 |
| S4 | 语义保真 | 非目标函数、信号、节点路径、碰撞/计分/收集链不得被无故删除或替换 |
| S5 | 有 Key 必经 LLM | 所有用户改游戏请求第一轮进入 LLM；确定性能力只能作为 LLM 可调用工具 |
| S6 | 品类隔离 | 注入材料与当前 genre 对齐；非 platformer 不出现 platformer 全局能力表 |
| S7 | 上下文高信号 | 文件树优先 core/scenes/config；不被 assets/.import/.agent 快照淹没 |
| S8 | 条件语义优先 | 「每 N 次/捡到才开/冷却/球速」先按条件机制规划，Catalog 仅材料 |
| S9 | salvage 不交半成品 | `gate_passed=false` 的代码不作为成功文件交付，不进入有效 harvest |
| S10 | 测试不假绿 | pass 必须包含入口、读盘、最小 diff、门禁、Godot、玩法保真证据 |
| S11 | 正向注入 | 工作法用正向动作描述；安全边界短、事实化，不劫持实现路径 |
| S12 | 七品类泛化 | 修复位于通用 Agent/工具层；品类只提供真实结构与验收锚点 |

### 2.2 明确不采用

- 不为「乒乓球色」新增 Intent 分支；
- 不把某个模板函数名写成全局 Agent 特例；
- 不依赖增加轮次掩盖首次破坏性写盘；
- 不以「最终能启动」代替玩法保真；
- 不恢复 Catalog express；
- 不修改冻结模板来迎合 Agent。

## 4. P0 详细施工方案

### HF12-01 · 读盘与回灌完整性

**当前问题**

1. `read_workspace_file(..., max_chars=12000)` 只返回文件头；虽然单文件有截断标记，但没有 offset/continuation 工具；
2. 多个 observations 在回灌时整体 `[:8000]`，可能把 JSON、文件正文和后续工具结果从中间切断；
3. 一轮同时读三个脚本时，模型可能只看到第一个脚本前半段，却误以为已掌握完整文件。
4. `read_reference_skill` 与声称证据 blob 也有独立长度上限，需统一采用结构化截断元数据。

**修复**

1. 扩展 `read_file` 参数：
   - `path: str`
   - `offset: int = 0`
   - `limit: int = 8000`
   - 返回 `total_chars / offset / returned_chars / eof / sha256 / content`
2. 增加 `search_in_file(path, query, max_hits, context_lines)`，先定位再分段读；
3. observations 按工具逐项序列化，不再对整个 JSON 字符串硬切；
4. 每个被缩略的 observation 必须返回 `truncated=true` 和 `next_offset`；
5. 当 LLM 尝试修改 `eof=false` 的已有文件时，门禁要求继续读取相关区段或改用精确 patch。

**代码落点**

- `backend/app/services/agent_workspace.py`
- `backend/app/services/creative/game_agent.py`
- `_AGENT_SYSTEM` 工具 schema
- `backend/tests/test_game_agent.py`

**验收**

- 读取 20k 字符脚本可通过两次分页完整恢复；
- 同轮读取多个文件，每个 observation 均保持合法 JSON；
- 测试不得出现裸 `[:8000]` 聚合硬切；
- 模型未读到 EOF 时，不能整写覆盖已有大文件。

### HF12-02 · 增加最小编辑工具

**当前问题**

提示要求「先 read、最小 write」，但工具只有整文件 `write_file`。对 200～500 行脚本，模型必须重新输出全部正文，天然引入截断和无关漂移。

**修复**

新增工具：

```json
{
  "tool": "replace_text",
  "path": "core/ball.gd",
  "old_text": "精确旧片段",
  "new_text": "替换后的片段",
  "expected_sha256": "read_file 返回的 sha256"
}
```

规则：

1. `old_text` 必须唯一命中；
2. 文件 hash 必须与最后一次读取一致，避免基于旧内容覆盖新改动；
3. 返回 `before_sha256 / after_sha256 / changed_lines / diff_preview`；
4. 已存在且超过阈值（建议 6k 字符或 120 行）的 `.gd/.tscn`，默认只允许 `replace_text`；
5. `write_file` 保留给：
   - 新文件；
   - 小型完整配置；
   - 模型已完整读取且明确需要整体重构的文件；
6. 整体重构须有 goal 明确支持，并通过 HF12-03 扩大改动门禁。

**代码落点**

- `agent_workspace.py`：hash、唯一替换、原子写；
- `game_agent.py`：工具定义、执行、observation；
- `agent_contracts.py`：整写限制与 diff 门禁；
- 单测：hash 冲突、零命中、多命中、精确替换、换行符。

### HF12-03 · Diff 与结构保真门禁

**当前问题**

Godot 能解析并不代表玩法没被改坏。现有门禁没有比较本轮前后结构，因此 Live 案例删除原碰撞函数并重写计分逻辑仍可成功。

**修复**

对已有 `.gd` 的本轮首个快照与候选版本做通用结构比较：

1. `extends / class_name / signal / @export / @onready` 清单；
2. 函数名清单与函数签名；
3. 场景关键节点与脚本绑定；
4. 本轮 goal/patch 触及函数集合；
5. 删除函数、删除信号、删除节点、修改非目标函数时生成 gate error；
6. 默认改动预算：
   - 非空白行变更比例 ≤ 20%；
   - 删除函数数 = 0；
   - 非目标函数体变化 = 0；
7. 若用户确实要求重构，可由 Agent 在 goals 中标记 `rewrite_scope`，但仍须先完整读盘并通过专门门禁；
8. 对七品类增加「关键链锚点」：
   - platformer：收集/受伤/玩家 group；
   - shmup：射击/碰撞/request_powerup/apply_powerup；
   - parkour：`_playing`/输入/碰撞；
   - survivor：`add_to_group("player")`/武器/刷怪；
   - fighting：输入/判定/血量；
   - racing：方向/速度/圈数；
   - pingpong：球拍反弹/计分/停球/PlayerPaddle。

**注意**

品类锚点只做门禁材料，不把具体用户现象写入 Intent。

**验收**

- 只给 `reset_to_center()` 增加颜色恢复可以通过；
- 同时删除 `_try_paddle_bounce()` 必须失败；
- 仅语法正确但替换计分方式必须失败；
- 七品类基线模板复制到 workspace 后均通过结构快照。

### HF12-04 · 写盘事务与即时回滚

**当前问题**

代码先写入真实 workspace，直到本轮含 done 才运行 Godot dry-run。若模型第一轮写坏、后续仍在思考，坏文件会作为中间态留在正在试玩的 workspace。

**修复**

1. 每次代码 mutation 前保存本动作快照；
2. 先在内存生成候选内容并执行：
   - 静态语法；
   - API 契约；
   - diff/结构门禁；
3. 原子替换目标文件；
4. 对 `.gd/.tscn` 立即执行轻量 Godot 校验；
5. 校验失败立即恢复该动作前快照，再把错误 observation 回灌；
6. 只有动作校验成功才加入 `written` 和开启软续杯；
7. done 阶段仍执行全项目 dry-run，作为最终组合验证。

**验收**

- 注入截断脚本后，磁盘自动恢复到动作前版本；
- `written` 不记录失败写；
- 用户在 Agent 处理中重开游戏，不会看到已知 parse-error 中间态。

### HF12-05 · Salvage 与交付语义

**当前问题**

当前 salvage 在 `loads_ok + written` 时可返回：

- `ok=true`
- `partial=true`
- `gate_passed=false`
- `sandbox_files=written`

这会让未过业务门禁但能加载的半成品继续留盘，也可能被上层当作「已改」展示。

**修复**

1. 建立本请求事务：
   - `committed_paths`：已过动作门禁；
   - `pending_paths`：尚未过最终门禁；
2. `gate_passed=false` 时默认回滚 pending；
3. salvage 只允许保留满足以下全部条件的 committed 子集：
   - 动作级校验通过；
   - 不依赖未完成的其它文件；
   - summary 明确 partial；
   - 不声称未完成 goal；
4. 上层 `_log_patch_result` 必须保留真实 `gate_passed/partial`；
5. harvest 硬条件增加 `gate_passed=true && partial!=true`；
6. 否定态/回滚态 `sandbox_files=[]`，可另记 `attempted_paths` 供诊断，不作为交付。
7. Kiosk 不得只看 `ok` 显示纯成功标题；`partial=true` 或 `gate_passed=false` 显示「完成一部分/尚未验收」，不显示成功交付态。

**验收**

- 轮次耗尽且最终门禁未过：workspace 恢复稳定版本；
- 返回 UI 文案诚实，但不会把 attempted 文件标为成功；
- Learned Skill 不收录 partial/rollback。

### HF12-06 · 有 Key 第一轮 LLM 与 drop-loot 校准

**当前冲突**

- 总纲 G1/G2：有 Key 第一轮进入 LLM；无快车道；
- 总纲 Q8：保留 drop-loot 专用路径；
- 当前代码：`run_game_agent` 在 `_llm_turn` 前直接调用 `_run_shmup_drop_loot_express()` 并 return。

**统一解释与修复**

Q8 的「保留专用路径」解释为**保留经过验证的确定性实现能力**，不解释为「绕过 LLM 的入口快车道」。

实施：

1. 移除 `run_game_agent` 中 pre-LLM return；
2. 将确定性逻辑封装为 LLM 可调用工具，例如：

```json
{"tool": "apply_shmup_drop_loot_chain", "skills": ["laser_beam", "bomb"]}
```

3. 第一轮仍由 LLM：
   - 理解「掉落才开」；
   - 读取 config/player/spawner；
   - 决定调用确定性工具或现场实现；
4. 工具内部继续保护 `powerup_types + apply_powerup + request_powerup + touch buttons`；
5. 通用掉落仍允许自由 GDScript；
6. 返回结果 `agent_rounds>=1`，工具轨迹可审计。

**验收**

- 有 Key 的 laser/bomb 掉落请求必须捕获到 `_llm_turn`；
- 不再出现 `agent_rounds=0`；
- 确定性工具结果仍通过 drop-loot 专用门禁；
- 无 Key stub 口径不变。

## 5. P1 上下文与路由施工方案

### HF12-07 · Catalog 品类隔离

当前 `sandbox_intent.CAPABILITY_CATALOG` 是 platformer 向全局表（如 `double_jump / ground_pound / coin_streak_buff`），但 `catalog_for_prompt()` 无 genre 参数，被七品类统一注入。

**方案**

优先选择：从 Agent 主上下文删除该全局表，统一使用 `contract.catalog_skills + Reference`。若保留，则改成 `catalog_for_prompt(genre, contract)` 并只返回：

- 当前品类真实 catalog；
- 当前品类桥能力摘要；
- 通用创作能力一句话。

**验收**

### HF12-08 · 高信号文件树

**方案**

   - `.import`
   - 大量音频/贴图资产
   - `.session_ai_log.jsonl`

3. 每目录限额，避免某一目录占满；
4. recent writes 始终单独置顶；
5. 支持 `list_dir(path)` 按需深入。

**验收**

- pingpong 必含 `core/ball.gd / paddle.gd / scenes/game.tscn`；

### HF12-09 · 注入去重与 token 预算

**方案**

1. System：只放稳定工作法 + 短安全边界 + 品类 10～20 行结构摘要；
2. User：用户原话 + diagnose + route 建议 + recent writes + 高信号树；
3. Reference 不再 system/user 双份注入：
   - system 仅注入索引/摘要；

4. Contract 只注入本轮相关 API/recipe，不默认粘贴全表；

**建议预算**

- system ≤ 6k 字符；
- 首轮 user 上下文（不含用户原话）≤ 4k；
- recent writes 不裁掉；
- 任何裁剪都有结构化标记。

### HF12-10 · 条件优先路由

**当前问题**

**验收**
