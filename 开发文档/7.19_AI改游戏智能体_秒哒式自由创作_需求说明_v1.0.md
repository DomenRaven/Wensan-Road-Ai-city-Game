## 0. 一句话

有 `LLM_API_KEY` 时，智能体必须像 **秒哒 / WorkBuddy**：先完整听懂用户原话并拆解 goals，再在会话副本上现场实现；**禁止**因命中「大力扣杀 / 激光 / 二段跳」等预制词就短路 enable catalog、丢掉触发条件与手感描述。Catalog 最多降级为可检索 **Skill 参考**，不是入口、不是能力天花板。

---

## 1. 问题与动机（拍板依据）

### 1.1 典型翻车对话（乒乓 · 大力扣杀）

| 用户 | 系统实际行为 | 用户损失 |
|------|--------------|----------|
| 我想要有大力扣杀的功能 | catalog express → 只 enable `power_smash` + 复读「点下方按钮」 | 未理解「要什么手感」 |
| 没感觉；希望每接 3 球用一次，速度很快，对面反应不过来 | **再次**命中扣杀词 → 又 enable + 同套话术 | 「每 3 球 / 三倍速 / AI」整句被丢掉 |
| 扣杀打不出来 / 没生效 | 仍可能 enable 或口头「已修复」 | 预制技能本身常不可感；Agent 改预制也难 |

### 1.2 根因（产品层）

1. **关键词捷径 > 整句理解**：`_can_catalog_express` / Intent A 硬 enable 抢在 LLM 拆解之前。  
2. **预制 ≠ 可玩**：HUD 按钮、充能、球速倍率等常未真正接线或与用户条件不符。  
3. **反馈被捷径吞掉**：「没生效」若仍带技能名，再次 express，禁止修盘。  

### 1.3 对标体验

| 秒哒 / WorkBuddy | 本产品应对齐 |
|------------------|--------------|
| 整句意图拆解后再动手 | `understanding` + `goals[]` 强制覆盖原话各子句 |
| 按需求写/改代码 | 会话 `core/scenes/config/ai_sandbox` 现场实现 |
| 工具/模板是助推不是替身 | Catalog / 桥 API / Learned Skill = **可选材料** |
| 失败继续改、不空话交差 | 不上锁；禁止「再 enable 一次」冒充修复 |

## 2. 已拍板决策（7.19）

| # | 议题 | 决策 |
|---|------|------|
| R1 | Catalog 快车道 | **有 Key 时默认关闭** 七品类 `_can_catalog_express` / 等价「点名秒开」路径 |
| R2 | Catalog 角色 | 降为 **Skill 参考库**（契约仍可列 id/label/runtime）；Agent **可选用**，**不得**因口语命中强制 enable |
| R3 | 主路径 | 一律：理解 → goals → 读盘 → 写会话副本 → 门禁 → 手动重开 |
| R4 | 用户附加条件 | 必须进入 goals 并落地（计数充能、倍率、时长、对手难度等）；禁止只开开关 |
| R5 | 「没生效」/故障 | Intent B / bugfix：diagnose + 修盘；**禁止**再 enable 同一 catalog 交差 |
| R6 | 无 Key 离线 | stub 可保留简单 enable（展厅演示）；与有 Key 主路径 **严格分离**，UI 诚实 stub |
| R7 | 预制技能质量 | 不保证「enable 即好玩」；产品不依赖预制可玩性做主验收 |
| R8 | 全局范围 | **七品类统一**（shmup/platformer/parkour/survivor/fighting/racing/pingpong） |
| R9 | 既有护栏 | 保留：幻想 API 禁、声称⊆磁盘、触屏 how_to_play、玩家健康 HF-10、Godot dry-run、salvage 不上锁 |

**不做（本切片）**：改 `templates/{genre}/core` 玩法源；自动晋升官方目录；为每个技能手写新 express；大规模 UI 改版。

## 3. 用户可见行为

### 3.1 正常改需求

1. 用户短对话说完整想法（可含条件、数值、手感）。  
2. UI 可见：理解一句话 + goals 列表（多条件拆开）。  
3. 智能体改会话副本；摘要说明 **做了什么 / 怎么玩**，须覆盖 goals。  
4. 用户点「现在重开游戏」试玩。  
5. 不满意 → 「没生效」或再说一句 → 继续 Agent，不换弱引擎。

### 3.2 禁止出现的话术/行为

- 用户已给出条件时，仍只回「已为你开启「大力扣杀」。点屏幕下方按钮」。  
- 连续多轮同一 skill 名，磁盘仅 `enabled_skills` 变化、无对应逻辑改动。  
- 「没生效」后再次「已开启 xxx」而无 diagnose/读盘证据。

### 3.3 验收口诀（7.19 追加）

**听全句 · 拆 goals · 写会话 · 条件落地 · 触屏可感 · 门禁过 · 手动重开 · 禁快车道顶替**

## 4. 工作流（有 Key）

```text
用户原话（整句）
  → understanding + goals[1..N]     # 条件/数值/手感各成 goal
  → 意图仅建议（可提示「类似 catalog:power_smash」）
  → 检索 Learned Skill（可选，相关才用）
  → 读盘 diagnose / read_file
  → 施工：写 core/scenes/config/ai_sandbox（优先实现机制本身）
       可选：引用 Skill 片段或桥 API；仅当 goals 等价「只要目录里那个开关」才 enable
  → self_check / dry_run / 玩家健康
  → done（summary 覆盖全部 goals）
  → UI → 手动重开
```

### 4.1 何时允许 `enable_catalog_skill`

**仅当同时满足**：

1. goals 明确只要「打开已有目录技能」、**没有**附加触发条件/手感/数值改写；或  
2. Agent 在理解中写明：先 enable 再叠加会话脚本实现用户条件；且最终磁盘能证明条件已实现。  

若用户说「每接 3 球扣杀一次、球速很快」→ **禁止**仅 enable；必须写计数与球速逻辑。

### 4.2 反例（大力扣杀）

| 用户原话 | goals（最低） | 禁止 | 要求落地 |
|----------|---------------|------|----------|
| 我想要有大力扣杀 | 有强力击球手段；触屏可触发 | 空 done | 会话实现或 enable+真接线 |
| 每接 3 球用一次，速度很快，对面反应不过来 | ①接球计数满 3 充能 ②触发后球速显著加快 ③对手难接 ④可触屏触发 | 只 enable `power_smash` | `paddle`/`ball`/`match_controller` 或沙箱脚本 |

## 5. 功能需求表

| ID | 需求 | 验收 |
|----|------|------|
| F1 | 关闭有 Key 的 catalog express | 口语「大力扣杀/激光/二段跳」不再 `agent_rounds=0` 秒开返回 |
| F2 | 整句进 goals | 多条件原话 → goals≥条件数；summary 覆盖 |
| F3 | Catalog 仅 Skill 提示 | 系统提示/路由可写「可参考 skill_id=…」；无强制 enable |
| F4 | 故障禁再开 catalog | 「没生效/打不出来」+ 技能名 → 不走 express、不 enable 交差 |
| F5 | 七品类一致 | 单测覆盖七品类：点名口语进 Agent 而非 express |
| F6 | 无 Key stub 隔离 | stub 路径可简单 enable；`provider=stub` 诚实 |
| F7 | 文档与开工 | 本需求 + 执行规范 + 开工提示词为 7.19 实施权威 |

## 7. 非目标 / 风险

- **风险**：去掉快车道后「开激光」平均轮次与耗时上升 → 可接受；用 Skill 检索与桥 API 降轮次，不恢复硬 express。  
- **风险**：LLM 仍可能自行 enable → 门禁/路由建议 + 反馈局硬禁 + 系统提示约束。  
- **非目标**：删除契约里的 catalog 列表；删除 optional_skills 目录文件。
